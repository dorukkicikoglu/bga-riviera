# Riviera: BGA adaptation

This folder is the BGA Studio project for **Riviera** (Valentin Demion, Helvetiq).
Game rules and every design decision live in `.claude/SPEC.md` (imported below, so it loads every session). Read it before writing game logic.
Per-milestone BGA Studio test checklists live in `.claude/TESTING.md`. The current milestone's implementation plan lives in `.claude/plans/`.

@SPEC.md

## Reference project: Fugu

`reference/fugu/` (inside this repo, gitignored and excluded from SFTP upload, like `misc/psd/`, the Photoshop sources) is my previous BGA game (same author, same publisher, same framework version).
**Riviera must be built to look like Fugu's code.** Before creating any file, open the Fugu equivalent and copy its structure, naming, and patterns. When in doubt, do what Fugu does.

Mirror these specifically:

- **Folder layout**: `src/ts/*.ts` and `src/scss/Game.scss` compiled by rollup/sass into `modules/js/Game.js` and `riviera.css`. Same `package.json` scripts, `rollup.config.mjs`, `tsconfig.json`. The template ships TS sources in `src-disabled/`; move them to `src/` like Fugu.
- **TS architecture**: one `Game.ts` that owns handler classes, one class per concern in its own file (`PlayerHandler`, `HandHandler`, `PlayedColumnHandler`, `DiceHandler` (Fugu's `CenterHandler`), `StartTokenHandler`, `TooltipHandler`, `PrefHandler`, `ModalBoxHandler`, `LogMutationObserver`, `EndGameScoringHandler`, ...), and client state classes under `src/ts/States/`. Reuse Fugu files as-is where they are truly game-agnostic (ModalBoxHandler, the core of LogMutationObserver). PrefHandler and TooltipHandler contain Fugu-specific code, so adapt them like the rest.
- **Logs**: same approach as Fugu. Notifications put `log-class-tag` markup into log strings and `LogMutationObserver` post-processes log divs (including replay logs and mobile chatbar). Card mentions in logs render as small card icons the way Fugu does it.
- **PHP**: namespace `Bga\Games\Riviera`, `Game.php` + `material.inc.php` + a `RIVTableManager.php` (like `FUGUTableManager.php`) for reading table state, one class per state in `modules/php/States/` using the new `GameState` class API exactly like Fugu's `PlayerTurn.php`, `NextPlayer.php`, `EndScore.php`.
- **Notifications**: same decorator in the `Game` constructor, same naming style, same way Fugu animates then resolves notifications on the client. Unlike Fugu, `setupPromiseNotifications({ minDuration: 1 })`: BGA's default holds every notification with log text for 500ms even when nothing animates, so a notification lasts exactly as long as its handler awaits a real animation (dice roll-in, deal and sweep, card slides, column and hand fades, Start token flight, end-game table). A handler with no animation (Stop/More reveal, banking, score updates, power log rows) must not await anything.
- **DB**: Deck component with a `cards` table, extra columns as needed, same style as Fugu's `dbmodel.sql`.
- **Code style**: tabs/spaces, brace style, camelCase, type annotations, comment style: match Fugu.

## Assets

- `img/riviera_cards.webp` is one sprite sheet: a 10-column x 7-row grid of 424x625 frames, row-major in this order:
  `[red 1..12] [green 1..12] [purple 1..12] [blue 1..12] [orange 1..12] [Last Chance] [card back]` (62 frames, rest of the last row blank).
  Compute `background-position` from an index (see SPEC.md > Sprite); never hardcode per-card positions.
- Dice have no art yet. Draw them in CSS (rounded square in the die color, pips or a number). Gold die for the golden die.
  Pips are 9 absolutely placed `.die-pip` spans of one fixed size (20% of `--die-size`), centered at 22%, 50% and 78% of the die on each axis, shown per `data-value` with `visibility: inherit` (never `visible`, which overrides a hidden die: the real die waiting hidden in its slot during the roll-in showed its new pips under the rolling copy). Never size pips with grid tracks or percentages (they came out uneven and oval before M3), and never give `.a-die` a % padding (a share of the parent's width, which blows the die up).
- `img/start_token.webp` is the Start token (a black pawn, portrait), fitted inside the 24x24px `#start-token` and the mini token in log rows (as big as the log card icons, `--log-card-icon-size`). It is also the mask of the token's outline rings (see Layout > Start token), which assumes the portrait pawn fills the token's height.
- `img/card_icon_numbers.webp` is the numbers 1 to 12 for the status bar card icon (`span.status-card-icon`): a 1 x 12 strip of equal 76x63 frames, left to right, gold with dark outlines on a transparent background (10 to 12 are wider glyphs inside the same frame width). Compute `background-position` from the value (see SPEC.md > Sprite). The icon keeps a visually hidden "<value> <color>" text for screen readers.- `img/power_icons_sprite.webp` (380x63, transparent) holds the 5 power icons left to right: cards 1, 2, 9, 10, 11. The frames are not equal (card 1 is narrower, card 10 wider and only 48px tall): their measured boxes live in the `$power-icons` SCSS map, and each icon is cut to its box and scaled to the same height. Re-measure if the image changes.
- `img/bg_trees.webp` (transparent) is the background palm trees: a 3 x 2 grid of equal cells, one tree per cell: teal, yellow, green, then orange, pink, purple. `background-size: 300% 200%`, `background-position` x 0/50/100%, y 0/100% (`data-tree-color` in `Game.scss`). The cell's aspect ratio is read from the image on load, never hardcoded. `BackgroundHandler.excludedTreeColors` lists the cells no tree uses (yellow for now); the sprite maths and the `Game.scss` rules keep all 6.

## Layout (client)

- **Background**: `img/bg_riviera.webp` (a seamless 1291x726 tile) on `body` (Fugu sets its background on `body` too): `background-size: 15% auto`, so each tile is 40% of the page width and it tiles sideways and vertically (never stretched), scrolls with the page (not `fixed`), with `#032a2e` (the tile's base teal) as the fallback color. Desktop (`body.desktop_version`) lays a 10% white layer over the same tile so it reads a little lighter, with `#ffffff` as its fallback color; mobile keeps the plain tile.
- **Palm trees** (`BackgroundHandler`, tunable constants at its top, one instance through `getInstance()`, created in `Game.setup`): swaying trees along the bottom of the screen in a fixed container, first in `<body>` at `z-index: 0` (like Fugu's background, so BGA's positioned content paints over it), `pointer-events: none`. Trees stand in the bottom left corner only: `minNumOfTrees` to `maxNumOfTrees` (4 to 7) of them, at random, heights descending left to right, from `edgeBleed` of the first tree's width off the left edge, each step `treeSpacing` +/- `spacingJitter` of the width of the tree just placed, squeezed so the last tree's right edge stays within `maxSpanOfWidth` (20%) of the screen's width. Random heights, the tallest at most `maxHeightRatio` times the shortest (`getHeightRange()` raises the min to enforce it), and random colors (never the same color on two neighbours left to right), taller trees further back. Each tree sinks `treeSinkRatio` of its height below the screen's bottom edge, pivot included, so no gap shows under the trunk as it rotates; the container stays as tall as the window and clips it. Sway: one injected `<style>` of baked `@keyframes` using `var(--sway)`, driven by CSS only (no `requestAnimationFrame`). **Every keyframe variant starts and ends upright, and every sway easing stops on each keyframe (never plain `ease` or `linear`)**: on `animationiteration` a tree may take a new variant at rest, with its delay reset to `0s` (the negative start delay would make it jump into the middle of the new cycle), and always a different variant name, since a new duration on the same running animation would jump. Rebuilt (debounced) only on crossing `mobileBreakpoint` or a `rebuildWidthChange` share of the width. `prefers-reduced-motion`: the trees stay, `animation: none !important` in `Game.scss`. The "Background trees" preference goes through `applyTreePreference()`: No wind is the same rule (`.no-wind`), No trees hides the container and removes the trees, and going back builds new ones.
- **Playable cards** glow; unplayable cards keep their normal look (no grey-out). Most glow gold (`--card-glow-color` / `--card-glow-peak-color`); playable power cards (1, 2, 9, 10, 11) glow light cream (`--power-card-glow-color` / `--power-card-glow-peak-color`) and further (`--power-card-glow-reach` 1.6, a multiplier of the glow keyframes' blur and spread, 1 for gold), so they differ by reach as well as color. Every card pulses in the one shared `--card-glow-duration` (3s), in phase: never a separate duration for power cards, and `HandHandler.syncCardGlow()` (on `animationstart`) puts a card that starts glowing while others already pulse onto their phase. The variables sit in `:root` in `Game.scss`. Only PlayCard's selections (first card and card-1 chain) get the power glow (`setSelectableCards(ids, 1, true)` adds `playable-power-card`); card 10's swap selection stays gold on every card. Same on mobile (only the glow size differs). The selected card (`selected-hand-card`) and the set-aside cards (`chosen-card`) both lift 14px and hold a still glow with no pulse (no outline): gold, or cream and further on a power card (`playable-power-card` while selected, the card's `data-value` once chosen). The selected card's is the pulse's peak (`--still-glow-size`, 11px, 8px on mobile), a chosen card's thinner, the pulse's lowest (`--chosen-glow-size`, 5px, 4px on mobile), so a confirmed card reads as settled. While a card is only selected, the other playable cards keep pulsing; once the play is confirmed they stop (the player is no longer active and `clearSelectableCards()` runs). While waiting for the others with an Undo button, the set-aside cards get `undoable-chosen-card` (`HandHandler.setChosenCardsUndoable()`, set once per `PlayCard.updateStatusBar()` rebuild and cleared on leaving the state, so it never outlives the choice): a click goes through the hand's one container listener to `PlayCard.chosenCardClicked()`, which calls the Undo button's own `UndoHandler.undo()`. They get a pointer cursor and nothing else: no hover effect, and no rule on their `transform`, `transition` or `filter` (a hover lift clashed with the set-aside lift). Their tooltip gets a "Click to undo your choice" line on top of the power reference (`.power-reference-hint`).
- **Selected card's dice**: in PlayCard, the dice that make the selected hand card playable glow gold (`--die-combo-glow-color` / `--die-combo-glow-peak-color`, a `box-shadow` on the die; no lift), class `.die-highlight-combo`, toggled on the existing dice by `DiceHandler.setComboHighlight(colors)` only (never re-rendered); the glow's transition (`--die-combo-transition-duration`, 150ms) sits on `#dice-container .a-die`, so it fades both ways (the card 9 preview glow, also a `box-shadow`, now fades in and out over it too). The server picks the dice (`RIVTableManager::getPlayableCardDice()`, which `getPlayableCardIDs()` wraps: card_id => die colors, the leftmost combination in the dice row, by leftmost die then the next) and sends them once as PlayCard's private `playableCardDice` (the dice and hand don't change in the state). Cleared on deselect, confirm, every status bar rebuild and leaving the state.
- **Game area order**, top to bottom: dice container, my hand, then one row of every player's played column (mine first, then turn order), wrapping onto more rows when they don't fit (always on mobile).
- Every player's played cards are visible (stacked vertically, overlapping so only the top strip with stars shows, as in the rules).

Once the owner has crashed, it shows a white `fa-bomb` (the crash log row's icon, as tall as the bank icon, `.played-column-bomb`) with no number on the same grey pill, with no opacity of its own (the crashed column is already at 0.45), and the tooltip "Crashed: no stars this round"; `notif_playerCrashed` switches the column to 'crashed' as soon as it arrives, before the cards fade out. It is driven only by `PlayedColumnHandler.setRoundStatus()` (setup from `round_status`, `stopOrMoreRevealed`, the next round's 'in'), with the crashed column's 0.4s opacity fade both ways.
- **Column header player** ("Show players as", pref 103, `PrefHandler.applyPlayersDisplay()`): one attribute, `data-players-display` (`avatar` / `name`) on `#played-columns-container`, switches every header together; never per column. Each header's `.played-column-player` (`#column-player-<id>`, `role="button"`, the BGA tooltip with the full name) holds both the avatar and the name, its click area 20% bigger than either both ways (a `::before` at `inset: -10%`, under the star badge's `z-index: 1`), and a click or Enter/Space calls `PrefHandler.togglePlayersDisplay()`, which applies at once, then saves with `bga.userPreferences.set()` (in a try/catch: a spectator may not be able to save); `userPreferences.onChange` applies the same value again. The avatar is BGA's `#avatar_<id>` src with its size suffix swapped to `_184` (`PlayedColumnHandler.fillAvatar()`), falling back to the board's own src, then to the name's initial on the owner's color. Avatar mode: a `--column-avatar-size` circle (31px, 39px on mobile) in the name's place, centered on the column's top border with a 3px ring in the owner's color. The star badge never moves: it stays docked top-right in both modes. The avatar fits the column's usual top padding and gaps, so switching modes moves nothing else.
- **Player boards** (BGA side panels) show the number of cards in hand, visible to everyone including spectators: with 7 cards or fewer (`MAX_INDIVIDUAL_CARD_BACKS`), one small card-back div per card, overlapping, like my game Odin, in a staircase (every 2nd back sits 4px lower; the backs are top-aligned so the margin moves them its full height); with more than 7, a single card back followed by "x N". Their size is `$hand-back-width` (20px) in `Game.scss`, with the overlap and the staircase step as shares of it (`$hand-back-overlap-ratio`, `$hand-back-step-ratio`, 0.2 each, so 4px). The Last Chance card (29px wide, 30% over the old 22px) sits to the right of the card backs, as far from the board's right edge as the backs are from its left (`PlayerHandler.updateLastChanceInset()`, measured from BGA's padding on every `onScreenWidthChange`), and disappears once used. Round status has no text row: nothing for in; out of the round, a stamp over the middle of the cards row (`.round-status-stamp`, uppercase, `rotate: -8deg`, 2px border, translucent white, fully opaque), shown only by `.riviera-player-board[data-round-status]`, so never both: "Stopped" (`.stopped-stamp`, blue `#1c4f72`) or "Crashed" (`.crashed-stamp`, red `#c62828`, a 1.6em `fa-bomb` on its left). Stopped also adds `stopped-player-board` to BGA's `.player-board` (`PlayerHandler.boardElement`), which greys the hand area (backs and Last Chance, `opacity: 0.45` + `grayscale(1)`), name, avatar and score untouched; a crash empties the hand count and leaves Last Chance as it is. The next round's `setRoundStatus('in')` clears both. **Score target**: a `.score-target` span ("/40", from `gamedatas.winningScore`, 0.75em, normal weight, opacity 0.6, on the score's baseline) sits right after BGA's score counter, never inside it, with the tooltip "First to ${points} ★ wins"; `PlayerHandler.updateScoreTarget()` alone places it (again, if BGA replaced the counter) and hides it once the score is past `WINNING_SCORE`, called from setup and `setScore()`. **End-game score**: every live score change goes through `PlayerHandler.setScore()` (never the counter's `toValue` directly); at `WINNING_SCORE` (sent as `gamedatas.winningScore`) or more the board gets `end-game-score-player-board` (score red `--end-game-score-color` and bold), and the counter (`.player-score-counter`, made inline-block, `scale` around the center, so no layout shift) pulses: crossing it live plays the intro (`.end-game-score-intro`, `end-game-score-beats`, two fast beats, 1.2s), and on its `animationend` the intro class gives way to the loop (`.end-game-score-loop`, `end-game-score-pulse`, 2s ease-in-out, infinite); both peak at the one `$end-game-score-peak-scale` (1.8), and the grown score paints over the star beside it without moving it and the board class, and over the "/40" (the counter is `position: relative; z-index: 1` inside its parent row, which is `isolation: isolate` so the 1 stays local: the "/40"'s opacity and the score's scale each make a stacking context, painted in DOM order, so without it the "/40" covered the score); while the intro or the loop runs (never with the static look), the board also burns (`burning-player-board`, a flamy yellow-red gradient scrolling on `flamy-background-animation`, white text shade on the name and score), toggled in `applyScoreHighlight()` with the score's classes; on load, in fast replay or a hidden tab, the loop alone. `PlayerHandler.updateEndGameScoreHighlight()` is the one decision (from the tracked score and `Game.isGameOver()`): game over or under the threshold, none; `prefers-reduced-motion`, static red and bold; otherwise the loop, never restarting a running one and letting a running intro finish. It is idempotent and called from setup, `setScore()` (which alone starts the intro, on a live crossing while the game goes on), every `onScreenWidthChange` (which also fires once BGA has finished loading) and the game end (`Game.updateEndGameScoreHighlights()`, from the `gameEnd` state class `States/GameEnd.ts` and from `EndGameScoringHandler.displayEndGameScore`, whose table arrives in EndScore just before `gameEnd`). `applyScoreHighlight()` is the only place that sets the classes, swapping one for the other so the two never run together, and keeps any clipping ancestor up to the board at `overflow: visible` while the score scales. The span is `getScoreElement()`, looked up again if the one held has left the page. **Once the game is over, every score goes back to BGA's default look** (no red, bold or pulse), and a page loaded after the end never gets any of it.
- **New round sequence**: in `newRound`, every column and the cards left in my hand sweep out off-screen at the same time, each group with its own stagger, and the notification waits for the last of them (`Game.sweepCardsOffScreen()`, `CARD_SWEEP_DURATION` 293ms each, `CARD_SWEEP_STAGGER` 32ms apart, quicker than the deal so the two read apart; a crash's hand and column sweeps use `CRASH_SWEEP_DURATION` 440ms and `CRASH_SWEEP_STAGGER` 29ms, ease-in-out; a crash's hand and column sweeps also start together); then `newHand` deals the new hand; once the last new card has landed, the dice roll (`diceRolled`). The sweep lifts the old cards out as copies at their on-screen places (`Game.animateSlideAway()`) and empties the hand at once (`HandHandler.discardAll()`). `newRound` does not touch the dice: last round's values stay up through the sweep and the deal, and only `diceRolled` changes them (the roll-in, see Dice container).
- **New hand deal**: a new round's hand (`newHand`) is dealt card by card, right to left (the rightmost card first, the leftmost last). `HandHandler.setHand()` lays the final hand out first (sorted and spaced) with every card hidden in its slot, then `animateSlide()` flies a copy of each card, at the hand-card size the whole way, and shows the real card when its copy lands, so no card moves during or after the deal. Every card travels the same path shifted to its own slot: a straight line from the top-left at `CARD_SWEEP_ANGLE` (10 degrees above horizontal, in `Game`), starting `DEAL_X_OFFSET` (1.2 window widths, more if that doesn't clear the screen's left edge) to the left of its slot and `dx * tan(angle)` above it (`Game.getOffScreenUpLeftRect()`). Each slides for `CARD_DEAL_DURATION` (440ms, `CARD_DEAL_EASING` ease-out) and the next starts `CARD_DEAL_STAGGER` (48ms) later (`HandHandler.dealIn()`). A card 10 redraw is a little slower, with its own `REDRAW_SWEEP_*` (550ms, 60ms apart) and `REDRAW_DEAL_*` (550ms, 100ms apart). The deal's geometry (`DEAL_X_OFFSET`, `DEAL_START_Y`) sits at the top of `HandHandler`; every card animation's durations, staggers and easings sit together at the top of `Game` (`CARD_SLIDE_*`, `CHAIN_CARD_STAGGER`, `SWAP_FADE_OUT_DURATION`, `BOARD_ARRIVAL_HOLD`, `BOARD_STACK_OFFSET`, `CARD_SWEEP_*`, `CARD_DEAL_*`, `REDRAW_*`), never in the handlers. The notification waits for the last card (and the sweep). No sweep or deal on page load / F5 or for spectators; the player boards' card-back counts just update.
- **Start token** is a single 24px element (`$start-token-size`), a badge overlapping the bottom-right corner of its owner's BGA avatar (3/4 of it over the avatar, clamped inside its anchor, so it never leaves the board at any width; it used to hang off the board's left edge, off-screen on mobile). Its anchor (`PlayerHandler.getStartTokenAnchor()`, class `start-token-anchor`) is BGA's `.player_board_inner`, made `position: relative` only if BGA leaves it static; with no `.player_board_inner`, the whole `.player-board`. Never the avatar's wrapper: BGA hides `#avatarwrap_<id>` (`display: none`) while the player is active and shows `#avatar_active_wrap_<id>` (the hourglass) in the same spot, so a token inside it vanished. `PlayerHandler.updateStartTokenPlace()` measures whichever of the two wrappers is showing (on setup and every `onScreenWidthChange`) into `--start-token-avatar-right` / `--start-token-avatar-bottom` on the anchor, and `Game.scss` places the token from them; unmeasured, it sits in the anchor's top-left inside corner. The flight's geometry (lift point, desktop or mobile layout) reads the `.player-board` around the anchor (`StartTokenHandler.getBoard()`); the card 10 bounce, the stopped and end-game classes live on that board too (`PlayerHandler.boardElement`, `positioned-player-board`). Tilted `TILT` (-7deg, to the left, the inline `rotate` property), above the board content and taking no layout space, so nothing shifts when it moves. Look (board, flying copy and the mini token in log rows alike): three child layers (`StartTokenHandler.LAYERS_HTML`), bottom to top a drop shadow (`.start-token-shadow`, the outlined silhouette again in 40% black shifted `0.5px 1.5px`, hidden on the mini token), a stroke in the owner's color (`--start-token-outline-width`, 3.5 : 34 of the token's size; color `--start-token-color`, set inline from the player color) and the pawn. No inner ring. No filters (stacked drop-shadows froze the browser once): the stroke and the shadow are layers bigger than the token by the stroke's width, masked by the token image 24 times (16 copies shifted by the width, 8 by half of it, `$start-token-ring-shifts`), so the union is the pawn grown evenly all around. In flight only the copy's stroke layer animates its `background-color` (Web Animations API, same timing as the flight): the old owner's color through the lift and the hold, blending into the new owner's through the landing. **Never use `transform` on the token or its copy**: movement, rotation and size each have their own CSS property, `translate`, `rotate` and `scale`, set and animated separately, with the copy rotating and scaling around its center (`.flying-start-token`, `transform-origin: 50% 50%`). The board tilt used to be `transform: rotate()`: the copy (a `cloneNode`) inherited it, so the copy's untransformed measurement came out rotated (37.9px instead of 34, shifted), its zoom read 1.115 instead of 1, and the whole path was pulled about 10% toward the viewport's top-left corner (a jump at the start and at the landing). The copy is the token's own (`createFlyingCopy()` / `getFlyingCopyPlacement()`), not `Game.createSlidingClone()`; its first keyframe is the real token's untilted on-screen center and height with `TILT`, its last the same on the new board. When it passes, a `position: fixed` copy flies in a single Web Animations API animation (`element.animate()`, linear between `KEYFRAMES_PER_PHASE` keyframes per phase sampled once in time, each phase eased in JS with quadratic curves). The path is two quadratic curves meeting at the lift point in the same direction: the lift, from the old corner out of the boards area, growing to 200% (`LIFT_SCALE`, `LIFT_DURATION` 520ms, easing in as it leaves the board), a hold at the peak at full size (`PEAK_PAUSE` ms of real stillness), then the landing, into the new owner's corner, shrinking back to 100% (`LAND_DURATION` 520ms, easing out as it arrives). Around the peak the phases ease into and out of the hold only as much as the pause calls for: `peakEasing = PEAK_PAUSE / PEAK_EASE_FULL_PAUSE` (300ms, capped at 1) blends the lift between ease-in and ease-in-out and the landing between ease-out and ease-in-out (`easeLift()` / `easeLand()`). At `PEAK_PAUSE` 0 the token crosses the peak at one steady speed (the control points scale with each phase's duration, so both sides match); never a cubic ease-in-out per phase, which added a ~200ms slowdown at the peak on top of the pause. The copy straightens from the tilt to upright in the first `STRAIGHTEN_FRACTION` (22%) of the lift and tilts back in the last `TILT_BACK_FRACTION` (22%) of the landing, done exactly as it lands. Rects are measured untilted (`getUntiltedRect()`). Boards beside the game area (desktop) lift sideways toward the game area, `DESKTOP_LIFT_DISTANCE` (140px) past the boards column, passing the lift point moving up or down (a C); boards above it (mobile) lift down to `MOBILE_LIFT_Y` (40%) of the viewport height, passing it moving sideways (a U; boards in one column get a loop of at least `MIN_CURVE_SPAN`). No `requestAnimationFrame` loop: the pass waits for the animation's `finished`, raced against a timeout (`FINISH_SAFETY_MARGIN`) so it always ends. Which layout is decided by where the boards are relative to `bga.gameArea.getElement()`, not by the screen width. The lift point is in viewport coordinates (always visible); the start and end are the boards' real on-screen places, even off-screen. The real token shows on the new board when the copy lands. The notification doesn't wait for that: `Game.startTokenFlight` holds the flight, the card 2/11 notifications and the roll play while it flies, `notif_diceRolled` awaits the roll and the flight together, and `notif_newRound` (the end-of-round pass has no roll after it) awaits the flight first. No flight on F5, or when `bgaAnimationsActive()` is false (fast replay, hidden tab). The constants sit at the top of `StartTokenHandler`.
- **Dice container** in the game area: show current roll, reserved dice (card 2) with a padlock badge (`.die-lock-badge-power2`, `DiceHandler.LOCK_BADGE_HTML_POWER2`, only on the dice area's dice and their fading copies: a disc in the reserver's color (`--lock-color`, set inline with `--reserver-color`) with a thin dark ring, 54% of `--die-size` (`--lock-badge-size` on `#dice-container`), centred on the die's bottom edge, a third over the die and two thirds below (`--lock-badge-below`), so it stays within the die's own width (never in the gap, a badge at the corner read as the next die's) and clears the bottom corner pips on every face, `pointer-events: none`, hidden while that die shows its card 9 arrows (the down arrow sits there); the padlock is an inline SVG of Font Awesome 6's lock (the log row's `fa-lock` glyph) at half the disc's diameter (27% of `--die-size`), white or black by the player color's luminance (`--lock-icon-color`, `getLockIconColorPOWER2()`); ## Conventions

- **Glossary**: use the terms in SPEC.md > Glossary in code comments, UI strings and docs. If I use a different word for one of them, treat it as the glossary term.
- **Power naming**: any field, DB column or variable that exists only because of a special power carries the power's card value in its name: `reserved_by_POWER2`, `modified_by_POWER9`, `in_use_by_POWER11`. Same suffix in PHP, SQL, TS and data attributes (`data-reserved-by-power2`).
- **Card ids reveal identity**: cards are inserted in a fixed order, so a `card_id` tells its color and value. Never send ids of cards a player isn't allowed to see; send counts instead.
- **Color order**: the `color` ENUM is declared in sprite order (red, green, purple, blue, orange), so `ORDER BY color, value` sorts like the sprite. Keep `CARD_COLORS` (PHP) and `$card-colors` (SCSS) in that same order.
- **Removed color**: in 2 to 4 player games its cards stay in `cards` at location `returned_to_box` and its die stays in `dice` with `die_location = 'returned_to_box'`. "Colors in use" is read from `dice`.
- **State ids**: RoundSetup 5, RollDice 10, ModifyDie 15, PlayCard 20, RevealCards 22, ResolvePowers 30, NextPOWER10Owner 33, SwapCards 35, PassStartToken 40, StopOrMore 50, RevealStopOrMore 55, EndRound 60, EndScore 98. (25 was BonusPlay, dropped in M3: the card-1 chain lives in PlayCard.)
- **Framework typing differs from Fugu's**: Riviera's `bga-framework.d.ts` is newer. `Player` has no `color_back` and `playerorder` is `number[]`. Ported helpers (`divYou`, `divColoredPlayer`) drop `color_back`.
- **No `gameui.isInterfaceLocked()`** in this framework version: use `this.game.isInterfaceLocked()`, which reads the `lockedInterface` body class.
- **Globals** go through `$this->bga->globals` (`startPlayerId`, `roundNumber`); Fugu has none. Throw `\Bga\GameFramework\SystemException`, not the deprecated `\BgaSystemException`.
- **Score display**: use BGA's default score counter (`bga.playerPanels.getScoreCounter(id)` when it changes), not a second `ebg.counter` like Fugu's `PlayerHandler`.
- **Scores on the server**: never touch `player_score` / `player_score_aux` with SQL (BGA's deploy check flags it): always go through `$this->bga->playerScore` (`get`, `getAll`, `getMax`, `set`, `setAll`, `inc`; pass `null` as the message when a game notification updates the counter itself). Don't write the column name in comments either.
- **Simultaneous choices**: a multiactive state stores each choice as pending `player` columns and never applies it there. The last chooser's `setPlayerNonMultiactive` moves to a GAME "reveal" state (`RevealCards`, `RevealStopOrMore`) that applies every choice and sends one notification. Undo goes through `RIVUndoManager` (`resetChoices` / `recordChoice` / `undo`) and the client `UndoHandler`; the revert action carries `#[PossibleAction]` + `#[CheckAction(false)]`.
- **Turn order and power timing** live in SPEC.md > Turn sequence (settled with Helvetiq). `RevealCards` reveals, checks Grand Slam, clears last turn's dice effects and marks pending powers, then stores the card 10 owners still `in` (this turn's crashes already applied) clockwise from the current holder (`saveOwnerOrderPOWER10()`, global `ownerOrder_POWER10`, a comma-separated string of player ids, computed once) and walks them through the GAME state `NextPOWER10Owner` (33, `goToNextPOWER10Owner()`; `RevealCards` and every `SwapCards` action go there, so `SwapCards` never re-enters itself, like Fugu's PlayerTurn → NextPlayer), ending in `StopOrMore`. Card 10 targets are opponents still `in`; the owner's later Stop doesn't matter. `RevealStopOrMore` applies the Stops and banks, then goes to `PassStartToken` (also reached from `StopOrMore` when everyone crashed), so the token passes once per turn, after Stop or More. Cards 2 and 11 resolve in the walk that `PassStartToken` starts (`RIVPowerManager::goToNextPreRollPower()`, clockwise from the new holder), only for players still `in`, ending in `RollDice`; with nobody in it goes to `EndRound`. Never resolve them right after the reveal, and never "cancel" a power on Stop: a stopper's power simply never resolves.
- **Private state args**: per-player data goes in `getArgs()` as `['_private' => [playerId => [...]]]`; the client reads `args._private`. Act methods take the magic `int $currentPlayerId` (multiactive) parameter.
- **Hidden-info notifications**: one `notify->all()` per event, never a `notify->player()` with the secret plus a public twin (that gave the players involved two log rows). The secret goes in the args as `'_private' => [playerId => [...]]` (`_ide_helper.php` > `Notify`): the framework sends each listed player only their own part, and everyone else, spectators included, gets the args without it. Don't merge it (no `alwaysMergePrivate()` / `_merge_private`): the client reads `args._private`, as for state args, and renders the faces when it is there and card backs when it isn't, in the handler and in the `createLog*` call in `bgaFormatText`. List `'_private'` in `preserve`. Public args carry ids and counts only, and the plain log text names no card. Card 10 (`cardsSwapped_POWER10`, `cardsRedrawn_POWER10`) is the example. Exception: a notification with no log row whose mere arrival would leak (the auto Grand Slam announcement while others still choose) goes through `notify->player()` alone, since a `notify->all()` with `_private` still reaches everyone, empty.
- **Logs**: every log type has a `${X_LOG_STR}` server placeholder (plain fallback text as its value, plus `preserve` for the args the row needs), one `LogMutationObserver.createLog*()` method, one `*-log` class, and one `--bg-log-*` variable in `:root` (listed in `$log-types` in `Game.scss`). - **Slide animations**: use `Game.animateSlide(element, from, to, ms, options)` for anything moving between containers (`from` may be a `DOMRect` on screen when there is no source element, like the deal's off-page start; `options` is a `SlideOptions`: `easing`, default `CARD_SLIDE_EASING` ease-in-out, `keepSize`, `delayMs`, `fadeOutMs`). `Game.animateSlideAway(element, toRect, ms, options)` is the reverse: a copy leaves element's place for a `DOMRect` and disappears, and element can be removed right after the call. Only the observers' card 10 card backs (mini back to mini back) use the default, at mini size both ways. `fadeOutMs` (`animateSlideAway`) fades the copy out once it has arrived (a card 10 card I give, on the other player's avatar). **A card that flies onto a player board** (avatar or hand count) stays there fully shown for `BOARD_ARRIVAL_HOLD` (100ms) before it fades or goes (`holdMs`). Never a tap, which selects the card: a tap also fires a synthetic hover, which is what used to bring the tooltip up. The click after a long press is swallowed, so it neither selects the card nor closes the dialog. `syncCardPowersDisplay()` swaps tooltips and dialog when a window crosses BGA's mobile width. Other tooltips (dice, log icons, Start token) stay tooltips.
- **Power prompts**: every power's status bar title is `Game.setPowerPromptTitle(card, isCurrentPlayerActive)`: `${you} may use ${card}` / `${actplayer} may use ${card}`, with the triggering card (the state args' `powerCard`, the owner's `getLastPlayedCard()`; the chain's last 1 for card 1) drawn as the circular card icon with its power badge (`Game.getStatusCardWithPowerHTML()`, see below: a ring in the card's color around its number, with `.card-power-badge` on its right edge, the same pair as "Play [card]?"; never the full-card sprite), both given the log mini cards' single-power tooltip through `addTooltipsToCardsIn('#pagemaintitletext')`. The details live in that tooltip, never in the title. The HTML goes in through `statusBar.setTitle(title, args)`, which substitutes args as raw HTML (Fugu's pass button slot does the same), so the translatable string only holds the placeholder. Keep buttons short ("Add golden die", "Skip"); steps inside a power get short titles of their own. Card 10's active owner gets its own two steps instead of the plain prompt: `${you} may choose 2 cards to swap ${card}` (or `... to discard`, `1 card` when only 1 can be drawn) with Skip alone, then, once the cards are selected, `Choose an opponent to swap ${cards}` (the selected cards' circular icons, with their power badges) with a `addPlayerChoiceButton` per target, or `Discard ${cards} and draw 2?` with Confirm, plus Skip. `SwapCards.updateStatusBar()` rebuilds both from the selection on every change; other players keep the plain prompt.
- **Card with its power badge** (status bar and reveal log row): `Game.getStatusCardWithPowerHTML(card)` returns the circular card icon with, for a power card (1, 2, 9, 10, 11), `Game.getPowerBadgeHTML(value)` attached: a `.card-power-badge` (an id and the `power-card-POWER<n>` class, so `addTooltipsToCardsIn` gives the whole badge the card icon's power tooltip) holding the power reference's `<span class="power-icon" data-power-value="N">`. Other cards get the card icon alone, unchanged. The two sit in one `.status-card-with-power` (inline-flex, so no whitespace gap and no line break between them). The badge is a cream square (`$card-power-badge-background`, the power cards' cream glow down to a soft gold), vertically centered on the circle's right edge, `$card-power-badge-scale` (0.66, 20% over the first 0.55) of the circle's diameter, `$card-power-badge-overlap` (0.25) of its width over the circle (the ring and the edge of its inside: on "10" and "11" it reaches about 2px into the glyph's right outline at 40px), `z-index: 1`, rounded corners, set off by a soft drop shadow plus a 0.5px faint dark ring (a `box-shadow`, never a border). The icon is fitted whole inside `$card-power-badge-icon-fill` (0.84) of it (`power-icon-fit()`: card 10, wider than tall, fills the width). Every size comes from the `card-power-badge($card-icon-size)` mixin, which takes a CSS variable or `calc()`: `$status-card-icon-size` in the status bar, `var(--log-card-icon-size)` in log rows, so it scales with the icon. The gap to a neighbouring card stays 6px (the badge's right margin plus the next card's). Used by the "You chose [cards]", "Play [card]?" / "Add [card]?", both card 10 swap or discard steps (selected cards included) and every power prompt (`setPowerPromptTitle`); the HTML goes in through `statusBar.setTitle(title, { card })`, then `addTooltipsToCardsIn('#pagemaintitletext')`. **Reveal log row**: the only log row with power badges (`getCardIconsHTML(cards, true)`, the same helper, card-1 chain cards included; card 9, card 10 and power-skipped rows keep the card icon alone, Last Chance its mini card, and the die tooltip's inline card 2 and the Keep Going button's disc never get one). A long chain wraps between groups, with the name and arrow centered on its first line (`line-height: var(--log-card-icon-size)`, `align-self: start`), while a Last Chance entry stays centered on its mini card. It keeps the log tooltip look through `processLogDiv`'s `addTooltipsToCardsIn(node)`.
- **Custom-colored action buttons** (`#stop-button`): only recolor them. Keep BGA's `.bgabutton` padding (`6px 12px`, BGA's `mainsite.css`) so they are as tall as the default buttons; never give them a height, and never restyle the neighbouring button to match. A glyph BGA's font lacks (★) is drawn from a fallback font with taller metrics and grows the button: wrap it in a `line-height: 0` span (`.button-star`). The Stop button starts with the bank icon (`Game.getBankIconHtml('button-bank-icon')`, `fa6 fa6-coins`: BGA loads Font Awesome 6.4 as `fa6 fa6-<name>` and 4.7 as `fa`, which has no coins), white like the label, placed like the Keep Going button's forward icon (`line-height: 0`, same gaps and drop), added in front of the translated label, never inside it. Only the Stop/More log row's bank icon is colored: muted rose `$log-bank-icon-color` (`#d9788f`); the button's and the banked column badge's stay white like their text (the badge's grey pill and its 0.6 opacity turn it light grey).
- **Keep Going's power icon**: `StopOrMore`'s private arg `powerCardNeedingMore` (`RIVPowerManager::getPowerCardNeedingMore()`, values in `POWER_VALUES_NEEDING_MORE`: 2, 9, 11) puts `Game.getStatusCardIconHTML()` after the translated label. The number is text in the label's font (`::before`, sized in `cqh` from the disc), not the sprite, whose numbers have dark shapes cut into them that turn into holes on white. The disc is placed absolutely between the button's top and bottom (3.5px inset, 5px from the right), so it follows the height, stays centered whatever the font and can't make the button taller, with `padding-right` keeping the label clear of it. - **Choose-a-player buttons** go through `Game.addPlayerChoiceButton(playerID, label, callback, params)`: BGA's secondary button plus `.player-choice-button` (white background, black text, a 2px ring and a soft glow in `--player-color`, set inline from the player's color; never per-player CSS; hover and active are a light `color-mix` tint of that color). BGA's gray gradient beats a plain class rule and comes back on hover and active, so `background-image`, `background-color`, `border-color`, `box-shadow`, `text-shadow` and `color` are `!important` in every state. The ring is a `box-shadow`, and BGA's border width, padding and radius are untouched, so the button is as tall and as round as Skip. The label is HTML with the player's name in `<b>` ("Swap with **name**"). Used by card 10's opponent buttons.
- **Undoing a logged action** (card 9 undo): no `undoSavepoint` / `undoRestorePoint`. Save what the undo needs (with `$this->bga->logs->getCurrentMoveId()` from the action) in a global, put that `move_id` in the logged notification so the row carries `data-move-id`, and on undo restore the DB, `inc(-1)` the stat, call `$this->bga->logs->remove($moveId)` (stored logs: F5, replays), and send a notification with no log text whose handler removes the row already on the page.
- **Zombies** are level 1 (report it in the Game Metadata Manager): every `zombie()` picks a random possible action with `getRandomZombieChoice()` among exactly the buttons a real player would see there (no greedy or "best" choice, no `getBestZombieChoice()`). A zombie that would stay active (a card-1 chain) finishes everything inside the same `zombie()` call, since the framework doesn't call it again.
- **Copyright header**: every PHP and TS source file starts with the same header as `Game.php` (BGA checklist).
