# Riviera: BGA adaptation

This folder is the BGA Studio project for **Riviera** (Valentin Demion, Helvetiq).
Game rules and every design decision live in `.claude/SPEC.md` (imported below, so it loads every session). Read it before writing game logic.
Per-milestone BGA Studio test checklists live in `.claude/TESTING.md`. The current milestone's implementation plan lives in `.claude/plans/`.

@SPEC.md

## Reference project: Fugu

`reference/fugu/` (inside this repo, gitignored and excluded from SFTP upload) is my previous BGA game (same author, same publisher, same framework version).
**Riviera must be built to look like Fugu's code.** Before creating any file, open the Fugu equivalent and copy its structure, naming, and patterns. When in doubt, do what Fugu does.

Mirror these specifically:

- **Folder layout**: `src/ts/*.ts` and `src/scss/Game.scss` compiled by rollup/sass into `modules/js/Game.js` and `riviera.css`. Same `package.json` scripts, `rollup.config.mjs`, `tsconfig.json`. The template ships TS sources in `src-disabled/`; move them to `src/` like Fugu.
- **TS architecture**: one `Game.ts` that owns handler classes, one class per concern in its own file (`PlayerHandler`, `HandHandler`, `PlayedColumnHandler`, `DiceHandler` (Fugu's `CenterHandler`), `StartTokenHandler`, `TooltipHandler`, `PrefHandler`, `ModalBoxHandler`, `LogMutationObserver`, `EndGameScoringHandler`, ...), and client state classes under `src/ts/States/`. Reuse Fugu files as-is where they are truly game-agnostic (ModalBoxHandler, the core of LogMutationObserver). PrefHandler and TooltipHandler contain Fugu-specific code, so adapt them like the rest.
- **Logs**: same approach as Fugu. Notifications put `log-class-tag` markup into log strings and `LogMutationObserver` post-processes log divs (including replay logs and mobile chatbar). Card mentions in logs render as small card icons the way Fugu does it.
- **PHP**: namespace `Bga\Games\Riviera`, `Game.php` + `material.inc.php` + a `RIVTableManager.php` (like `FUGUTableManager.php`) for reading table state, one class per state in `modules/php/States/` using the new `GameState` class API exactly like Fugu's `PlayerTurn.php`, `NextPlayer.php`, `EndScore.php`.
- **Notifications**: same decorator in the `Game` constructor, same naming style, same way Fugu animates then resolves notifications on the client.
- **DB**: Deck component with a `cards` table, extra columns as needed, same style as Fugu's `dbmodel.sql`.
- **Code style**: tabs/spaces, brace style, camelCase, type annotations, comment style: match Fugu.

## Assets

- `img/riviera_cards.webp` is one sprite sheet: a 10-column x 7-row grid of 424x625 frames, row-major in this order:
  `[red 1..12] [green 1..12] [purple 1..12] [blue 1..12] [orange 1..12] [Last Chance] [card back]` (62 frames, rest of the last row blank).
  Compute `background-position` from an index (see SPEC.md > Sprite); never hardcode per-card positions.
- Dice have no art yet. Draw them in CSS (rounded square in the die color, pips or a number). Gold die for the golden die.
  Pips are 9 absolutely placed `.die-pip` spans of one fixed size (20% of `--die-size`), centered at 22%, 50% and 78% of the die on each axis, shown per `data-value`. Never size pips with grid tracks or percentages (they came out uneven and oval before M3), and never give `.a-die` a % padding (a share of the parent's width, which blows the die up).
- `img/start_token.webp` is the Start token (a black pawn, portrait), fitted inside the 34x34px `#start-token` and the 14x14px mini token in log rows. It is also the mask of the token's outline rings (see Layout > Start token), which assumes the portrait pawn fills the token's height.
- `img/card_icon_numbers.webp` is the numbers 1 to 12 for the status bar card icon (`span.status-card-icon`): a 1 x 12 strip of equal 76x63 frames, left to right, gold on an opaque `#05141a` background (10 to 12 are wider glyphs inside the same frame width). Compute `background-position` from the value (see SPEC.md > Sprite). The icon keeps a visually hidden "<value> <color>" text for screen readers.
- `img/power_icons_sprite.webp` (380x63, transparent) holds the 5 power icons left to right: cards 1, 2, 9, 10, 11. The frames are not equal (card 1 is narrower, card 10 wider and only 48px tall): their measured boxes live in the `$power-icons` SCSS map, and each icon is cut to its box and scaled to the same height. Re-measure if the image changes.

## Layout (client)

- **Background**: sea blue gradient on `body` (Fugu sets its background on `body` too).
- **Playable cards** glow; unplayable cards keep their normal look (no grey-out). Most glow gold (`--card-glow-color` / `--card-glow-peak-color`, pulse `--card-glow-duration` 3s); playable power cards (1, 2, 9, 10, 11) glow light cream with a slower pulse (`--power-card-glow-color` / `--power-card-glow-peak-color`, `--power-card-glow-duration` 4.2s), so they differ by rhythm as well as color. The variables sit in `:root` in `Game.scss`. Only PlayCard's selections (first card and card-1 chain) get the power glow (`setSelectableCards(ids, 1, true)` adds `playable-power-card`); card 10's swap selection stays gold on every card. Same on mobile (only the glow size differs). Selection, set-aside and chosen-card styles are unchanged.
- **Game area order**, top to bottom: dice container, my hand, then one row of every player's played column (mine first, then turn order), wrapping onto more rows when they don't fit (always on mobile).
- Every player's played cards are visible (stacked vertically, overlapping so only the top strip with stars shows, as in the rules).
- **Player boards** (BGA side panels) show the number of cards in hand, visible to everyone including spectators: with 6 cards or fewer, one small card-back div per card, overlapping, like my game Odin; with more than 6, a single card back followed by "x N". The Last Chance card sits to the right of the card backs and disappears once used. Also show round status (in / stopped / crashed) and the Start token.
- **New round sequence**: the previous round's columns clear (`newRound`); then, at the same time, the cards left in my hand sweep out to the left, all together, off-screen (`OLD_HAND_SWEEP_DURATION`, 200ms) and the new hand is dealt; once the last new card has landed, the dice roll (`diceRolled`). The sweep lifts the old cards out as copies at their on-screen places (`Game.animateSlideAway()`) and empties the hand at once, so the new hand is laid out right away while the copies fly off. `newRound` does not touch the dice: last round's values stay up through the sweep and the deal, and only `diceRolled` changes them (the roll-in, see Dice container).
- **New hand deal**: a new round's hand (`newHand`) is dealt card by card, right to left (the rightmost card first, the leftmost last). `HandHandler.setHand()` lays the final hand out first (sorted and spaced) with every card hidden in its slot, then `animateSlide()` flies a copy of each card, at the hand-card size the whole way, and shows the real card when its copy lands, so no card moves during or after the deal. Every card travels the same path shifted to its own slot: it starts `DEAL_X_OFFSET` (1.2 window widths) to the left of its slot, at the same page y `DEAL_START_Y` (document, not viewport: by default just above the top of the page, off-screen when scrolled down). Each slides for `DEAL_DURATION` (400ms, `DEAL_EASING` ease-out) and the next starts `DEAL_STAGGER` (100ms) later. These constants and the sweep's sit together at the top of `HandHandler`. The notification waits for the last card (and the sweep). No sweep or deal on page load / F5 or for spectators; the player boards' card-back counts just update.
- **Start token** is a single element, absolutely placed on the top-left corner of its owner's whole BGA player board (`PlayerHandler.getStartTokenAnchor()`: the `.player-board` around our panel, given `start-token-anchor`), tilted `TILT` (-7deg, to the left, the inline `rotate` property), above the board content and taking no layout space, so nothing shifts when it moves. Look (board, flying copy and the mini token in log rows alike): two child layers (`StartTokenHandler.LAYERS_HTML`), bottom to top a stroke in the owner's color (`--start-token-outline-width`, 3.5px; 1.4px on the mini token; color `--start-token-color`, set inline from the player color) and the pawn. No inner ring. No filters (stacked drop-shadows froze the browser once): the stroke is a layer bigger than the token by its width, masked by the token image 24 times (16 copies shifted by the width, 8 by half of it, `$start-token-ring-shifts`), so the union is the pawn grown evenly all around. In flight only the copy's stroke layer animates its `background-color` (Web Animations API, same timing as the flight): the old owner's color through the lift and the hold, blending into the new owner's through the landing. **Never use `transform` on the token or its copy**: movement, rotation and size each have their own CSS property, `translate`, `rotate` and `scale`, set and animated separately, with the copy rotating and scaling around its center (`.flying-start-token`, `transform-origin: 50% 50%`). The board tilt used to be `transform: rotate()`: the copy (a `cloneNode`) inherited it, so the copy's untransformed measurement came out rotated (37.9px instead of 34, shifted), its zoom read 1.115 instead of 1, and the whole path was pulled about 10% toward the viewport's top-left corner (a jump at the start and at the landing). The copy is the token's own (`createFlyingCopy()` / `getFlyingCopyPlacement()`), not `Game.createSlidingClone()`; its first keyframe is the real token's untilted on-screen center and height with `TILT`, its last the same on the new board. When it passes, a `position: fixed` copy flies in a single Web Animations API animation (`element.animate()`, linear between `KEYFRAMES_PER_PHASE` keyframes per phase sampled once in time, each phase eased in JS with quadratic curves). The path is two quadratic curves meeting at the lift point in the same direction: the lift, from the old corner out of the boards area, growing to 200% (`LIFT_SCALE`, `LIFT_DURATION` 520ms, easing in as it leaves the board), a hold at the peak at full size (`PEAK_PAUSE` ms of real stillness), then the landing, into the new owner's corner, shrinking back to 100% (`LAND_DURATION` 520ms, easing out as it arrives). Around the peak the phases ease into and out of the hold only as much as the pause calls for: `peakEasing = PEAK_PAUSE / PEAK_EASE_FULL_PAUSE` (300ms, capped at 1) blends the lift between ease-in and ease-in-out and the landing between ease-out and ease-in-out (`easeLift()` / `easeLand()`). At `PEAK_PAUSE` 0 the token crosses the peak at one steady speed (the control points scale with each phase's duration, so both sides match); never a cubic ease-in-out per phase, which added a ~200ms slowdown at the peak on top of the pause. The copy straightens from the tilt to upright in the first `STRAIGHTEN_FRACTION` (22%) of the lift and tilts back in the last `TILT_BACK_FRACTION` (22%) of the landing, done exactly as it lands. Rects are measured untilted (`getUntiltedRect()`). Boards beside the game area (desktop) lift sideways toward the game area, `DESKTOP_LIFT_DISTANCE` (140px) past the boards column, passing the lift point moving up or down (a C); boards above it (mobile) lift down to `MOBILE_LIFT_Y` (40%) of the viewport height, passing it moving sideways (a U; boards in one column get a loop of at least `MIN_CURVE_SPAN`). No `requestAnimationFrame` loop: the pass waits for the animation's `finished`, raced against a timeout (`FINISH_SAFETY_MARGIN`) so it always ends. Which layout is decided by where the boards are relative to `bga.gameArea.getElement()`, not by the screen width. The lift point is in viewport coordinates (always visible); the start and end are the boards' real on-screen places, even off-screen. The real token shows on the new board when the copy lands, and the notification waits for that. No flight on F5, or when `bgaAnimationsActive()` is false (fast replay, hidden tab). The constants sit at the top of `StartTokenHandler`.
- **Dice container** in the game area: show current roll, reserved dice (card 2) with the owner's color, golden die when active, and dice modified by card 9. A die is never shown without a value (`.a-die[data-value=""]` is `display: none`, in the container and in log rows), and the dice area shows the last roll until the next one: only a roll blanks a die (`applyDieData(..., isRoll)`), so the golden die keeps its face after it expires at the reveal and leaves with the next roll. It appears with the roll that gives it a value, never on the card 11 confirm (`goldenDieAdded_POWER11` carries no dice, and its log row names the golden die in words).
- **Dice roll-in** (`diceRolled`, `DiceHandler.rollDice()`): at the same moment, every shown die leaves a copy in place (`.fading-out-die`, absolutely placed, prepended so the new dice pass over it) that fades `opacity` to 0 and `scale` to `FADE_OUT_SCALE` (`FADE_OUT_DURATION` 300ms) and is removed, and every die of the new roll (golden die included) slides in from past the container's right edge (`ROLL_START_GAP` die sizes beyond it, `ROLL_START_LIFT` above its row), turned `ROLL_MIN_SPIN` to `ROLL_MAX_SPIN` degrees either way, to 0 (`ROLL_DURATION` 450ms, `ROLL_EASING` ease-out with no overshoot, a random delay up to `ROLL_MAX_DELAY`, `fill: 'backwards'` so it waits off-screen). Web Animations API on `translate` and `rotate` only, never `transform`; screen px converted with the die's measured zoom (BGA's mobile scaling). The face shows `ROLL_FACE_CHANGES` random values on the way and the real one from `ROLL_FACE_SETTLE_FRACTION` of the travel. `#dice-container` is `position: relative; overflow-x: clip; overflow-y: visible`: the dice come in from the game area's edge, never over the player boards, with no sideways scroll on mobile (`clip`, not `hidden`, keeps the vertical axis visible). The notification awaits every die (raced against `FINISH_SAFETY_MARGIN`). No roll-in on load/F5 or when `bgaAnimationsActive()` is false: the dice just change. A card 9 change is not a roll: `updateDice()` with the quick `die-changed` scale. `getDieDiv()` only matches dice in a `.die-slot`, never a fading copy. Constants at the top of `DiceHandler`.
- **Card 9 arrows**: the active card-9 owner gets a small filled triangle centered above (+1) and below (-1) each die that can still be turned this roll (0.442 × the die width, height 0.62 × that); other players and spectators see none. Each arrow is a transparent hit container (`.die-arrow`, z-index above the die) holding its visible triangle (`.die-arrow-triangle`): the up one runs from the triangle's tip down to the die's middle line, the down one from that line to its tip, so together they cover the arrows, the gaps and the die with no dead zone. Clicking a container selects that choice: the arrow stays highlighted and the status bar reads "Turn [die] 4 → 5?" with "Confirm" and "Skip". Another choice switches the selection, the selected one again clears it, "Confirm" sends `actModifyDie_POWER9`; with the "One-click card play" preference on, the click sends it at once. Hovering a container lights its triangle; its title shows the result ("6 → 1"). The dice themselves have no click or hover handlers. While a choice is selected its die previews the value it would become, with a soft glow (`previewed-die-power9`) and no animation (previewing and restoring change the face instantly; `die-changed` plays only for real changes from the server), local to the owner only: one die at a time, and the real value stays in `DiceHandler.diceData` (the status bar die icon and the tooltip use it), so switching, clearing, "Skip", leaving the state, a reload or any server dice update (`updateDice` calls `ModifyDie.cancelSelection()`) restores it. Each die sits in a `.die-slot`; `showModifyArrowsPOWER9` adds the two containers (absolutely placed) only for the active owner in ModifyDie, on modifiable dice, and `hideModifyArrowsPOWER9` removes them, so everywhere else the dice and their tooltips are untouched. `#dice-container` always reserves the arrow height plus the gap above and below the dice, in every state, so the dice never move: 3px above, 5px below (the die's drop shadow falls 2px below it, so the gaps look equal).

## Conventions

- **Glossary**: use the terms in SPEC.md > Glossary in code comments, UI strings and docs. If I use a different word for one of them, treat it as the glossary term.
- **Power naming**: any field, DB column or variable that exists only because of a special power carries the power's card value in its name: `reserved_by_POWER2`, `modified_by_POWER9`, `in_use_by_POWER11`. Same suffix in PHP, SQL, TS and data attributes (`data-reserved-by-power2`).
- **Card ids reveal identity**: cards are inserted in a fixed order, so a `card_id` tells its color and value. Never send ids of cards a player isn't allowed to see; send counts instead.
- **Color order**: the `color` ENUM is declared in sprite order (red, green, purple, blue, orange), so `ORDER BY color, value` sorts like the sprite. Keep `CARD_COLORS` (PHP) and `$card-colors` (SCSS) in that same order.
- **Removed color**: in 2 to 4 player games its cards stay in `cards` at location `returned_to_box` and its die stays in `dice` with `die_location = 'returned_to_box'`. "Colors in use" is read from `dice`.
- **State ids**: RoundSetup 5, RollDice 10, ModifyDie 15, PlayCard 20, RevealCards 22, ResolvePowers 30, SwapCards 35, PassStartToken 40, StopOrMore 50, RevealStopOrMore 55, EndRound 60, EndScore 98. (25 was BonusPlay, dropped in M3: the card-1 chain lives in PlayCard.)
- **Framework typing differs from Fugu's**: Riviera's `bga-framework.d.ts` is newer. `Player` has no `color_back` and `playerorder` is `number[]`. Ported helpers (`divYou`, `divColoredPlayer`) drop `color_back`.
- **No `gameui.isInterfaceLocked()`** in this framework version: use `this.game.isInterfaceLocked()`, which reads the `lockedInterface` body class.
- **Globals** go through `$this->bga->globals` (`startPlayerId`, `roundNumber`); Fugu has none. Throw `\Bga\GameFramework\SystemException`, not the deprecated `\BgaSystemException`.
- **Score display**: use BGA's default score counter (`bga.playerPanels.getScoreCounter(id)` when it changes), not a second `ebg.counter` like Fugu's `PlayerHandler`.
- **Scores on the server**: never touch `player_score` / `player_score_aux` with SQL (BGA's deploy check flags it): always go through `$this->bga->playerScore` (`get`, `getAll`, `getMax`, `set`, `setAll`, `inc`; pass `null` as the message when a game notification updates the counter itself). Don't write the column name in comments either.
- **Simultaneous choices**: a multiactive state stores each choice as pending `player` columns and never applies it there. The last chooser's `setPlayerNonMultiactive` moves to a GAME "reveal" state (`RevealCards`, `RevealStopOrMore`) that applies every choice and sends one notification. Undo goes through `RIVUndoManager` (`resetChoices` / `recordChoice` / `undo`) and the client `UndoHandler`; the revert action carries `#[PossibleAction]` + `#[CheckAction(false)]`.
- **Turn order and power timing** live in SPEC.md > Turn sequence (settled with Helvetiq). `RevealCards` only reveals, checks Grand Slam, clears last turn's dice effects and marks pending powers, then goes to `StopOrMore`. `RevealStopOrMore` applies the Stops and banks, then goes to `PassStartToken` (also reached from `StopOrMore` when everyone crashed), so the token passes once per turn, after Stop or More. Cards 2, 10 and 11 resolve in the walk that `PassStartToken` starts (`RIVPowerManager::goToNextPreRollPower()`, clockwise from the new holder), only for players still `in`, i.e. who chose More, ending in `RollDice`; with nobody in it goes to `EndRound`. Never resolve them right after the reveal, and never "cancel" a power on Stop: a stopper's power simply never resolves.
- **Private state args**: per-player data goes in `getArgs()` as `['_private' => [playerId => [...]]]`; the client reads `args._private`. Act methods take the magic `int $currentPlayerId` (multiactive) parameter.
- **Logs**: every log type has a `${X_LOG_STR}` server placeholder (plain fallback text as its value, plus `preserve` for the args the row needs), one `LogMutationObserver.createLog*()` method, one `*-log` class, and one `--bg-log-*` variable in `:root` (listed in `$log-types` in `Game.scss`).
- **Slide animations**: use `Game.animateSlide(element, from, to, ms, easing)` for anything moving between containers (`from` may be a `DOMRect` on screen when there is no source element, like the deal's off-page start; `easing` defaults to `ease-in-out`). `Game.animateSlideAway(element, toRect, ms, easing)` is the reverse: a copy leaves element's place for a `DOMRect` and disappears, and element can be removed right after the call. Both share the same clone and transform code. The flying copy changes size on the way: it starts at the on-screen size of `from` (a hand card, or the top mini card back when `from` is a player board's hand count) and lands at exactly the size and place of `element`, so nothing jumps at the end. Measure everything with `getBoundingClientRect()` (on-screen px) and move the copy with one `transform` (translate + scale): the copy lives in `<body>`, outside BGA's mobile scaling of the game area, so it converts screen px with its own measured zoom (`getBoundingClientRect().width` / unrounded computed width; `offsetWidth` rounds and drifts by a pixel). Never animate `left`/`top` or rely on the copy's CSS size matching the destination.
- **Mobile sizing (like Fugu)**: `gameinfos` keeps `game_interface_width.min` at 740, so BGA lays the game out at 740px or more and scales it down on a phone. Card and die sizes on `.mobile_version` are therefore large logical sizes: `--card-width: min(28.5vw, 150px)` (Fugu's value) and `--die-size: min(13.3vw, 55px)` (the desktop die/card proportion). Played columns use the same `--card-width` and wrap. My hand is always one horizontal line, every card at the same height, overlapping horizontally so the whole hand fits the container width; the only vertical movement is a selected or set-aside card being raised. On mobile `HandHandler.applyMobileCardSpacing()` (Fugu's) sets inline %-margins so the row spans 99% of the hand width (never spreading a short hand, never covering more than 85% of a card); no zig-zag. Desktop keeps the `--hand-card-overlap` logic. Both run from `recomputeCardSpacing()` after any hand change, and debounced from `Game.onScreenWidthChange`.
- **One-shot animation classes** (fade-ins, fade-outs, `die-changed`) must be removed once they have played: a leftover one becomes the element's fallback `animation` and replays whenever another animation (like the playable glow) stops applying. Found in M3: the new hand's `cards-fading-in` class stayed on, so confirming a card (which stops the playable glow) replayed the fade-in on the whole hand, as if it re-rendered. (That fade-in is gone since: the new hand is dealt, see Layout.)
- **`dbmodel.sql` comments**: put them on their own `--` lines, never after a `;` and never containing a `;`. BGA splits the file into statements itself and silently dropped an `ALTER` that had a trailing comment.
- **Statistics** go through `$this->game->bga->playerStats` / `->tableStats` (Fugu uses `$this->game->playerStats`). Every stat is initialized in `setupNewGame` except `lastChanceRound`, which is left unset on purpose so games without a Last Chance don't skew its average. A power's stat carries the power suffix (`powerUsed_POWER2`).
- **Tooltips**: tooltips only reach elements already on the page, and need an id on each element (`createCardDiv` / `createLastChanceDiv` give one). Every card in the game area (my hand, every played column) gets the power reference (`getPowerReferenceHTML`, the rulebook's powers page: entries grouped by timing, icon floated left, the hovered card's power highlighted; one cached HTML per highlighted value). Call `tooltipHandler.addTooltipsToCards()` after any notification that creates cards. Log mini cards keep a single-power tooltip, added per row by `LogMutationObserver` through `addTooltipsToCardsIn(node)`. Safari mobile gets the same reference HTML at the bottom of the page instead.
- **Power prompts**: every power's status bar title is `Game.setPowerPromptTitle(card, isCurrentPlayerActive)`: `${you} may use ${card}` / `${actplayer} may use ${card}`, with the triggering card (the state args' `powerCard`, the owner's `getLastPlayedCard()`; the chain's last 1 for card 1) drawn as the circular card icon (`Game.getStatusCardIconHTML()`, `.status-card-icon`: a ring in the card's color around its number, the same icon as "Play [card]?"; never the full-card sprite) and given the log mini cards' single-power tooltip through `addTooltipsToCardsIn('#pagemaintitletext')`. The details live in that tooltip, never in the title. The HTML goes in through `statusBar.setTitle(title, args)`, which substitutes args as raw HTML (Fugu's pass button slot does the same), so the translatable string only holds the placeholder. Keep buttons short ("Add golden die", "Skip"); steps inside a power get short titles of their own ("Choose 2 cards to swap"). Card 10's buttons show from the start, disabled until the cards are selected, so swap vs. discard-and-draw is visible before the first click.
- **Custom-colored action buttons** (`#stop-button`): only recolor them. Keep BGA's `.bgabutton` padding (`6px 12px`, BGA's `mainsite.css`) so they are as tall as the default buttons; never give them a height, and never restyle the neighbouring button to match. A glyph BGA's font lacks (★) is drawn from a fallback font with taller metrics and grows the button: wrap it in a `line-height: 0` span (`.button-star`).
- **Zombies** are level 1 (report it in the Game Metadata Manager): a zombie that would stay active (a card-1 chain) finishes everything inside the same `zombie()` call, since the framework doesn't call it again.
- **Copyright header**: every PHP and TS source file starts with the same header as `Game.php` (BGA checklist).
- **Deleting or renaming PHP files**: SFTP now runs with `autoDelete: true`, so a file removed locally is removed on Studio on the next sync. Still check after a delete or rename: the framework loads every class in `modules/php/States/`, and a stale state class collides on its state id (the template's `PlayerTurn.php` took id 10 and broke game creation once `RollDice` used 10).
